🔒 How the Hash Chain Works

A plain-English visual explainer for the Tamper-Evident Logging System (Task 1)

⚙️ Step 1 — How a "Stamp" (Hash) is made
Each log entry has a HASH — its unique stamp. It is made by running all the entry's data through the SHA-256 algorithm. The magic part: the previous entry's HASH is mixed in. This links every entry to its parent.
HASH = SHA256( prev_hash + timestamp + event_type + description )
// Change ANY one of these → the HASH completely changes → chain breaks
✅ Step 2 — A Normal, Untampered Chain
Each block's PREV HASH (left column) is an exact copy of the block above's HASH (right column). When the system verifies, it just checks: "Do these two numbers match?"

🔴 Step 3 — What happens when a Hacker edits Row 2?
The hacker opens the JSON file and changes Row 2's description text to hide their tracks. Here's what happens next:
📄 Row 2 — BEFORE (original)
Description "Admin authenticated from 127.0.0.1"
Hash (stamp) f381cd1449...fb0a49
Row 3's Prev Hash f381cd1449...fb0a49 ✓ matches
→
🔥 Row 2 — AFTER (hacker edits text)
Description (changed!) "[HACKER] Entry deleted — nothing to see"
Hash (re-computed by system) XXXXXX...NEWSTAMP ← completely different!
Row 3's Prev Hash (still old) f381cd1449...fb0a49 ✗ NO LONGER MATCHES!
→
🚨 Verification Result
System checks Row 3 prev_hash == Row 2 hash?
f381cd... ≠ XXXXXX...

🔴 TAMPERED at entry 3!

📝 One-Sentence Summary for Each Rule

✏️
Text is edited: The hash of that entry changes → the next entry's prev_hash no longer matches → detected as TAMPERED
🗑️
Entry is deleted: The next entry is now pointing to a prev_hash that no longer exists in the file → detected as CHAIN BROKEN
🔀
Entries are swapped: The time order of hashes is disrupted → detected as CHAIN BROKEN at the swapped position
✅
Nothing is changed: Every prev_hash perfectly matches the hash of the row above it → CHAIN INTACT
